## 0. 한 줄

지금 허브는 **도구**로 나뉘어 있다 — 「관상 보기」 「손금 보기」. 사람이 앱을 여는 이유는 도구가
아니라 **질문**이다 — 「그만두고 싶은 게 일 때문인지 사람 때문인지 모르겠다」. 인기테마운세는
그 질문을 카드 제목으로 올리고, **기존 엔진의 출력을 그 질문에 맞게 잘라서** 답한다.

도구는 없애지 않는다. 질문을 **앞에** 세우고 도구를 **뒤로** 옮긴다.

### 1-3. 결론 — 만들 것은 «엔진»이 아니라 «질문 층»

계산기는 충분하다. 없는 것은 **「이 질문에는 엔진의 어느 출력을 어떻게 자를 것인가」** 라는 층이다.
인기테마운세 = 그 층의 이름이다.

## 2. 정의 — 기존 분석과 무엇이 다른가

|             | 기존 분석 (도구 축)                 | 인기테마운세 (질문 축)                               |
| ----------- | ----------------------------------- | ---------------------------------------------------- |
| 카드 제목   | 「관상」 「손금」 「재물운」        | 「버는 만큼 남지 않는 이유」                         |
| 사용자 상태 | 무엇을 볼지 이미 정한 사람          | **고민만 있고 뭘 봐야 할지 모르는 사람**             |
| 진입 동기   | 도구에 대한 호기심                  | 지금 자기한테 있는 통증                              |
| 결과 형태   | 그 도구가 낼 수 있는 것 전부        | **그 질문에만 답한다** — 안 물어본 것은 안 쓴다      |
| 재방문      | 도구를 다 쓰면 끝                   | 고민이 바뀌면 다시 온다 (테마를 계속 추가할 수 있다) |
| 확장        | 도구를 새로 만들어야 늘어난다(비쌈) | **테마 상수 1건 + 썸네일 1장이면 늘어난다**(쌈)      |

핵심: 인기테마운세는 **새 계산이 아니라 새 편집**이다. 같은 사주에서 다른 질문에 답한다.

## 3. 허브 재편 — 두 섹션을 세 섹션으로

### 3-1. 지금 구조와 CEO 지시

현재 `components/analysis/AnalysisDashboard.tsx` 는 두 섹션이다.

| 섹션                    | 상수           | 카드                                                              |
| ----------------------- | -------------- | ----------------------------------------------------------------- |
| 「청담해화당 통합분석」 | `STUDIO_CARDS` | 궁합 · 관상 · 손금 · 풍수 (4장)                                   |
| 「더 깊이 들여다보기」  | `MENU_CARDS`   | 2026 병오년 · 고민상담 · 재물 · 애정 · 직장 · 학업 · 부동산 (7장) |

CEO 지시는 **「청담해화당 통합분석」 자리를 인기테마운세로** 바꾸라는 것이다.
🔴 그런데 그 섹션은 **궁합·관상·손금·풍수의 유일한 허브 진입 경로**다. 카드를 지우면
관상·손금·풍수는 허브에서 사라진다(스튜디오 페이지 직접 URL로만 남는다). 반드시 살린다.

### 3-2. 설계 — 3섹션

```
[사주 유도 카드] [오늘의 정성] [절기 배너]        ← 그대로

① 인기테마운세                                   ← 새 섹션 (구 「통합분석」 자리)
   와이드 카드 3장(16:9) + 「테마 전체 보기」
   └ 지금 사람들이 가장 많이 묻는 것

② 무엇으로 볼까요                                ← 구 STUDIO_CARDS 승계 (이름만 바뀜)
   궁합 · 관상 · 손금 · 풍수 (4장, 2열) — 카드·링크·아이콘 무손실

③ 더 깊이 들여다보기                             ← 구 MENU_CARDS 정리
   2026 병오년 · 고민상담 · 오늘의 운세 (3장)
   └ 재물/애정/직장/학업/부동산 5장은 ①로 흡수 → 목업 라우트 소멸

[오늘의 운세 카드]                                ← 그대로
```

**왜 이 배치인가**

- ①은 «고민이 있는 사람»을, ②는 «도구를 아는 사람»을 받는다. 두 입구가 다 필요하다.
- ②의 이름을 「무엇으로 볼까요」로 바꾸면 ①과 위계가 자연스럽다(질문 → 도구).
  「청담해화당 통합분석」이라는 이름은 ①로 넘어간 게 아니라 **없어진다** — 그 이름은
  4개 도구를 묶는 설명으로도 부정확했다(통합분석은 삼합 리포트가 따로 있다).
- ③은 «주기가 있는 것»(연·일)과 «대화»만 남는다. 성격이 섞이지 않는다.

## 4. 테마 카드 공통 규격 ★ 다른 기(機)는 이 표를 그대로 채운다

테마 하나 = 아래 **11칸을 전부 채운 것**. 하나라도 비면 미완성이다.

```
### T-{n} 「후킹 제목」

| 칸               | 값                                                                    |
| ---------------- | --------------------------------------------------------------------- |
| id               | kebab-case 영문 (라우트 slug · 상수 키 · 썸네일 파일명이 전부 이 값)   |
| 카테고리         | career | wealth | love | family | health | study                     |
| 후킹 제목        | 14~22자. 질문형 또는 상황형. **결과 단정 금지**(§9-1)                 |
| 서브카피         | 28~44자. 「누가·언제」를 넣어 자기 얘기로 만든다                       |
| 썸네일 컨셉      | 한 문장 + 생성 프롬프트 초안(§10 규칙)                                |
| 타깃             | 누구인가 + 그 사람이 이 카드를 누르는 순간의 상태                      |
| 근거(리서치)     | 실제 고민이라는 증거 + URL. 없으면 「추측」이라고 적는다               |
| 풀이 설계        | L1 결정론 입력 → L2 판정 규칙 → L3 AI 계약 (§5. 「AI가 알아서」 금지) |
| 결과 화면        | 섹션 순서 + 각 섹션이 L1/L2/L3 중 무엇에서 나오는지                    |
| 복채 단가        | 제안값 + 근거(§7 표에서 파생)                                          |
| 🔴 법적 체크     | 표시광고법·업권법·금지어·고지 — 해당 없으면 「해당 없음」이라고 적는다 |
```

### 4-1. 후킹 제목 작성 규칙

CEO 톤 예시 3개가 기준선이다. 그 결을 유지하되 **효과를 단정하는 절반은 버린다**.

| 규칙                     | 좋은 예                                      | 나쁜 예                          |
| ------------------------ | -------------------------------------------- | -------------------------------- |
| 상황을 묘사한다          | 「사람 하나 잘못 들여 휘청인 적 있으신가요」 | 「연매출 10억 껑충」 (효과 단정) |
| 사용자의 말투를 훔친다   | 「나갈까 말까, 벌써 세 번째」                | 「이직운 상세 분석」 (도구 이름) |
| 양자택일의 괴로움을 쓴다 | 「접을까 버틸까」                            | 「폐업 시기 진단」 (결과 단정)   |
| 자책을 대신 말해준다     | 「버는 만큼 남지 않는 이유」                 | 「재테크 성공 비법」 (효과 단정) |
| 물음표로 열어둔다        | 「제 탓일까요」                              | 「당신은 ~한 사람입니다」 (단정) |

금지: 숫자 성과(「10억」 「3배」) · 보장 어휘(「반드시」 「확실히」 「성공」) ·
비교우위(「최고의」 「유일한」) · 금지어 5종(§9-3) · 의료/법률/투자 판단 어휘.

### 4-2. 결과 화면 공통 골격

모든 테마가 같은 뼈대를 쓴다. 다른 것은 «채우는 내용»뿐이다.

```
1. 히어로        — 테마 제목 + 썸네일 + 대상자 이름                     [정적]
2. 한 줄 답      — 이 질문에 대한 한 문장                               [L3]
3. 지표 3종      — 밴드(낮음/보통/높음) + 근거 한 줄                    [L1→L2]
4. 지금 상황     — 왜 그런가 (원국 근거를 쉬운 말로)                     [L2→L3]
5. 시기          — 언제가 열리고 언제가 막히나 (연·월)                   [L1→L2]
6. 할 일 3가지   — 구체적 행동                                          [L3]
7. 되짚기        — 과거 역추산 1건 (「작년 그때 ~하셨죠」)               [L1→L3]
8. 다음 걸음     — 관련 테마 2장 + 고민상담 진입                        [정적]
9. 면책 고지     — ServiceDisclaimer (+ 테마별 추가 고지)               [정적]
```

§4-2의 3번을 **숫자 점수로 노출하지 않는다**(밴드 + 막대 길이만). 이유는 §9-1.

## 5. 풀이 설계 규약 — 엔진 재사용 지도

> 🔴 **새 AI 프롬프트를 처음부터 쓰지 않는다.** 과거 교훈(종합 기능에 개별 엔진 재사용 필수)이
> 그대로 적용된다. 인기테마운세는 «엔진 출력을 자르는 규칙»이지 새 계산이 아니다.

### 5-1. 3층 구조

```
L1  결정론 (기존 엔진, 순수 함수)      같은 사주 → 항상 같은 값. 테스트로 고정.
      ↓ 테마별로 필요한 것만 뽑는다
L2  판정 (테마 룰, 새로 쓰는 유일한 코드)  순수 TS · 30줄 내외 · 단위 테스트 필수
      ↓ 확정된 사실로 넘긴다
L3  서술 (AI)                          계산 금지. 확정 사실을 «문장»으로만 만든다.
```

**L3에 반드시 박는 지시문**(전 테마 공통):

```
아래 [확정 판정]은 이미 계산이 끝난 값이다. 다시 계산하지 말고, 숫자를 새로 만들지 말고,
판정과 어긋나는 서술을 하지 마라. 당신의 일은 이 판정을 사람의 말로 풀어 쓰는 것뿐이다.
```

이 한 줄이 「AI가 알아서 써준다」와 「엔진이 판정하고 AI가 옮겨 적는다」를 가른다.
AI가 점수·시기를 스스로 만들면 **같은 사주에 다른 답**이 나오고, 그 순간 서비스는 신뢰를 잃는다.

### 5-2. L1 — 쓸 수 있는 결정론 출력 전량

| 엔진 파일                         | 함수 / 타입                                | 꺼내 쓸 필드                                                                                                                                                                                                                         |
| --------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `saju-engine/context-builder.ts`  | `buildSajuContext(person)` → `SajuContext` | 아래 전부의 컨테이너. `promptContext`(AI 주입 텍스트)까지 완성해 준다                                                                                                                                                                |
| ↳ `sipseong.ts`                   | `analyzeSipseong` → `SipseongMap`          | `items[]`(위치·글자·오행·십성) · **`distribution`**(십성별 개수) · `dominantSipseong` · `strengthAssessment`(신강/신약/중화) · `bodyStrengthScore`(0-100)                                                                            |

### 5-3. L2 — 테마 판정의 공통 원시형

테마마다 자기 규칙을 쓰되 **출력 타입은 하나**로 통일한다. 결과 화면 §4-2가 이 타입만 알면 된다.

```ts
/** 지표 — 결과 화면 3번 칸. 테마당 정확히 3개. */
interface ThemeIndicator {
  key: string // 'bigeop_pressure'
  label: string // '경쟁 압력'
  score: number // 0~100 (내부값 — 화면에 숫자로 쓰지 않는다)
  band: 'low' | 'mid' | 'high' // 화면에 나가는 것은 이것과 막대 길이뿐
  basis: string // '비견 2 · 겁재 1 — 여덟 글자 중 셋'  ← L1에서 그대로 파생
}

/** 시기 — 결과 화면 5번 칸. */
interface ThemeTiming {
  kind: 'opportunity' | 'caution'
  year: number
  months: number[] // calculateYearlyFortune 의 keyOpportunity/CautionMonths
  basis: string // '세운 정관이 용신과 합' ← sipseongRelation·yongsinAffinity 파생
}

/** 테마 판정 = L3에 넘기는 확정 사실 뭉치. */
interface ThemeVerdict {
  themeId: string
  indicators: [ThemeIndicator, ThemeIndicator, ThemeIndicator]
  timings: ThemeTiming[] // 기회 1~2 + 주의 1~2
  ruleHits: string[] // rule-base 강매치 룰 이름
  pastHint: { period: string; basis: string } | null // 과거 역추산 근거(문장은 L3가 쓴다)
}
```

**밴드 경계는 테마 상수에 박고 테스트로 고정한다.** 경계가 코드 곳곳에 흩어지면
「같은 사주인데 화면마다 다른 밴드」가 난다.

### 5-4. L3 — AI 계약

- **프롬프트 조립**: `buildMasterPromptForAction(person, analysisType, userContext, additionalContext, outputFormatGuide)`
  를 그대로 쓴다. 새 빌더를 만들지 않는다.
- **`analysisType`**: 기존 유니온을 재사용한다 — `TREND_CAREER`(직장 계열) · `TREND_WEALTH`/`WEALTH_DEEP`(재물 계열) ·
  `COMPATIBILITY`(2인 테마). 🔴 **테마마다 새 `AnalysisType` 을 추가하지 않는다** —
  `getAnalysisTypeGuide()` 가 Record 전수 매핑이라 늘어날수록 유지비가 붙고, 테마는 계속 늘어날 것이다.
- **테마 고유 지시는 `additionalContext` + `outputFormatGuide` 두 인자로만 주입한다.** 이 두 자리가
  테마의 «자기 목소리»이고, 그 밖의 것은 전부 공용이다.
- **`additionalContext` 에 넣는 것**: ①§5-1 고정 지시문 ②`ThemeVerdict` JSON ③테마 질문 문장
  ④금지 소재(테마별) ⑤말투 규율(기존 trend 프롬프트 승계 — 「~합니다/~입니다」체, 무속 어휘 금지, 긍정 70 : 주의 30).
- **출력**: JSON 고정. 공통 스키마:

```jsonc
{
  "themeId": "...",
  "headline": "질문에 대한 한 문장 답", // 결과 2번
  "situation": "왜 그런가 — 3~4문장", // 결과 4번
  "indicatorNotes": ["지표1 해설", "지표2", "지표3"], // 결과 3번 보조 (밴드는 L2가 이미 정함)
  "timingNotes": ["기회 해설", "주의 해설"], // 결과 5번 보조
  "actions": ["행동1", "행동2", "행동3"], // 결과 6번
  "pastEcho": "작년 ~하셨을 겁니다 — 1~2문장", // 결과 7번 (pastHint 없으면 빈 문자열)
  "caution": "이 풀이를 어떻게 쓰면 안 되는지 1문장",
}
```

- **점수·월 숫자를 AI가 쓰지 못하게 한다**: `actions`/`timingNotes` 안의 월 표기는 `ThemeTiming.months`
  에 있는 값만 허용. 파싱 후 **서버에서 검증**하고 어긋나면 L2 값으로 덮는다(조용히 틀린 달을 내보내지 않는다).

### 5-5. 2인 테마(궁합 재사용) 추가 규약

- `FOCUS_GROUPS.WORK`(상사-직원·동료·멘토·알바) / `.BUSINESS`(동업·투자·거래처·팀)를 **그대로** 쓴다.
- `forbidden`(연애 소재 전면 금지)·`placesLabel`(「합이 트이는 협업 방식」)이 이미 정의돼 있다.
- 🔴 2인 테마는 §9-2(채용절차법)를 반드시 통과해야 한다. 「뽑아라/자르라」가 아니라 **이미 함께 있는 사람과의 소통**이다.

## 6. 확장 규칙 — 테마를 계속 늘리는 구조

### 6-1. 데이터 주도 vs 코드 상수 — **코드 상수(TS)로 간다**

| 항목            | DB 테이블(데이터 주도)                              | TS 상수 ← **채택**               |
| --------------- | --------------------------------------------------- | -------------------------------- |
| 카피 수정 속도  | 어드민에서 즉시                                     | 배포 필요                        |
| 표시광고법 방어 | 🔴 **없음** — 운영자가 위험 문구를 쓸 수 있다       | ✅ 금지어 테스트가 CI에서 막는다 |
| 풀이 설계(L2)   | 🔴 DB에 못 담는다 — 결국 코드가 따로 필요           | ✅ 판정 규칙과 카피가 한 파일에  |
| 과거 사고 이력  | 🔴 어드민 플랜 편집기 오라벨 → 표시광고법 사고(9차) | —                                |
| 시드 소실 위험  | 🔴 DB 재구축 때 어드민 작성분 전멸 전력             | ✅ 리포에 있다                   |

> 결정 근거: 인기테마운세의 카피는 **법적 리스크가 붙은 문구**다. 9차에 「매일 복채」·「무제한 상담」
> 사고가 난 곳이 정확히 «어드민이 자유롭게 쓸 수 있던 자리»였다. 카피와 판정을 한 파일에 묶고
> 테스트로 지키는 편이 싸다.

### 6-2. 단일 출처 파일

```
lib/domain/theme-fortune/
  themes.ts              ← 테마 정의 전량 (id·카피·카테고리·썸네일·단가·analysisType·금지소재)
  verdict-types.ts       ← §5-3 타입
  rules/{themeId}.ts     ← 테마별 L2 판정 (순수 함수 1개 export)
  __tests__/
    themes.test.ts       ← 금지어·글자수·id 유일성·썸네일 파일 존재·단가 유효성
    rules/*.test.ts      ← 판정 규칙 결정론 (같은 입력 → 같은 출력)
```

**테마 하나 추가 = ① `themes.ts` 항목 1개 ② `rules/{id}.ts` 1개 ③ 썸네일 2장 ④ 테스트 통과.**
화면·라우트·저장·공유는 손대지 않는다(전부 공용 골격).

### 6-3. 「인기」의 정의 — 순서를 무엇으로 정하나

허브 ①에 3장만 걸린다. 무엇을 거는가?

| 단계 | 방식                                                   | 조건                 |
| ---- | ------------------------------------------------------ | -------------------- |
| v1   | **`themes.ts` 의 `rank` 수동값**(CEO/기획이 정함)      | 지금                 |
| v1.5 | + **절기·시즌 가중**(연말=이직, 연초=재물, 3월=신학기) | 시즌 로직 이미 있음  |
| v2   | 최근 30일 실행 수 기반 자동 정렬                       | 계측이 먼저(§11 T-4) |

🔴 v1에서 **「인기」라는 말이 거짓이 되지 않게** 한다 — 실행 수를 근거로 정렬하지 않는 동안

분류 이름이므로 허용, 「이번 주 1위」 「N명이 봤어요」는 **v2 전까지 금지**(표시광고법).

## 7. 복채·캐시·재분석 정책

### 7-1. 단가 — 기존 표에서 파생

현행(`lib/domain/payment/feature-costs.ts`, 단위 만냥): 사주 2 · 궁합 2 · 관상 2 · 손금 2 · 풍수 2 ·
재물 5 · 이미지 5 · 삼합 5 · 신년 0 · 오늘 0.

**인기테마운세 제안 — 3단**

| 단     | 단가         | 무엇이 들어가나                               | 해당 테마                            |
| ------ | ------------ | --------------------------------------------- | ------------------------------------ |
| 맛보기 | **0 (무료)** | 1인 사주 · 지표 3종 + 한 줄 답까지만 (AI 1회) | 카테고리당 1종 «미끼» (§11에서 지정) |
| 기본   | **2만냥**    | 1인 사주 전체 골격 9섹션                      | 직장·재물 1인 테마 대부분            |
| 관계   | **3만냥**    | 2인 궁합 엔진 + 관계군 프롬프트               | 2인 테마 (궁합 단가 2 + 관계 편집 1) |

근거: 인기테마운세 1회 = 마스터 프롬프트 1회 + 엔진 계산(무료). 기존 1인 분석(사주·관상 2만냥)과
같은 원가 구조다. 재물 심층 5만냥은 «다중 섹션 + 투자 시기»라 더 무겁다 — 인기테마는 그보다 얇으므로
2만냥이 정합적이다. **5만냥은 쓰지 않는다**(같은 값이면 재물 심층과 구분이 안 된다).

🔴 표시 = 실차감 원칙: 단가는 반드시 `feature-costs.ts` 에 키를 추가해 파생시킨다.
`themes.ts` 에 숫자를 직접 쓰면 그 순간 6곳이 어긋났던 옛 사고가 재발한다.

### 7-2. 캐시·재분석

| 항목        | 정책                                                                                                                                                                                                   |

## 8. 공유(OG) 설계

배선은 **이미 다 있다**. 새로 만들 것이 없다.

| 조각               | 현황                                                                       | 인기테마운세에서 |
| ------------------ | -------------------------------------------------------------------------- | ---------------- |
| `/api/og`          | `title·desc·score·name·category` 쿼리로 1200×630 생성(edge, Noto Serif KR) | 그대로 사용      |
| `/share/[token]`   | `analysis_history.share_token` 으로 조회 + `generateMetadata`              | 그대로 사용      |
| `share_view_count` | 조회수 집계 있음                                                           | 그대로           |

**설계 결정 3개**

1. **OG 제목 = 테마 후킹 제목**(사람 이름 아님). 공유는 「내 결과」가 아니라 「이 질문」이 퍼져야 한다.
   → `title = 테마 제목`, `desc = headline`(AI 한 줄 답에서 개인 식별 표현 제거).
2. 🔴 **점수를 OG에 싣지 않는다.** `score` 파라미터를 비운다. 밖으로 나가는 이미지에 숫자가 박히면
   §9-1의 «효과 단정» 노출면이 가장 넓어진다.
3. 🔴 **기존 버그 하나**: `/share/[token]` 의 OG 제목이 `record.category` 를 **그대로** 쓴다 →
   「TODAY 운명 분석」 「WEALTH 운명 분석」처럼 영문 enum이 노출된다. `THEME` 을 추가하면
   「THEME 운명 분석」이 나간다. 한글 라벨 매핑을 같이 넣는다(작업 1줄).

## 9. 🔴 법적 규율 — 설계에 박아야 하는 것

> 오늘(2026-08-12) 기능 하나(`/business` 「채용·승진 적합도」)를 이 사유로 **삭제했다.**
> 인기테마운세는 그 삭제된 주제와 **정확히 같은 땅**을 밟는다. 프레이밍이 전부다.

### 9-1. 표시광고법 — 효과를 단정하지 않는다

CEO 톤 예시 「직원만 잘 뽑아도 연매출 10억은 껑충!!!!」은 **그대로 못 쓴다.**
운세 결과에 따른 매출 증대를 광고하면 실증 책임이 발생하고, 실증할 방법이 없다.

**변환 규칙**

| 단정 (금지)                     | 상황·질문 (허용)                                    |
| ------------------------------- | --------------------------------------------------- |
| 「연매출 10억 껑충」            | 「사람 하나 잘못 들여 회사가 휘청인 적 있으신가요」 |
| 「이직 성공 시기 알려드립니다」 | 「나갈까 말까 — 지금이 그 때인지」                  |
| 「부자 되는 사주 확인」         | 「버는 만큼 남지 않는 이유」                        |
| 「투자 적기 진단」              | 「돈 앞에서 나는 어떤 사람인가」                    |

추가 규율:

- **숫자 점수를 전면에 걸지 않는다**(§4-2). 「85점」은 측정 방법을 제시할 수 없는 수치다.
  밴드(낮음/보통/높음)는 «이 풀이 안에서의 상대 표현»으로 읽히므로 안전 폭이 넓다.
- **「인기」의 실측 주장 금지**(§6-3) — v2 계측 전까지 「1위」 「N명」 금지.
- 🔴 **기존 재물 분석의 `investmentTiming`(bestMonth/bestWeek/avoidMonth)은 재검토 대상**이다.
  라이브 코드가 이미 «투자 적기»를 특정 주 단위로 지시한다. 인기테마운세는 이 형식을
  **승계하지 않는다**(§9-4 참조). 기존 화면의 처리는 CEO 결정 큐(§12-5)로 올린다.

### 9-2. 🔴 채용절차법 — 사장-직원 테마를 살리는 유일한 프레이밍

**판단 근거**

| 법                     | 내용                                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 채용절차법 제4조의3    | 구인자는 **직무 수행에 필요하지 않은** 정보(신체적 조건·출신지역·혼인여부·재산, 직계존비속과 형제자매의 학력·직업·재산)를 요구·수집 금지. **과태료 500만원 이하** |
| 고용정책기본법 제7조 ① | 모집·채용 시 합리적 이유 없이 **성별·신앙·연령·신체조건·사회적 신분·출신지역·학력·출신학교·혼인·임신·병력** 등을 이유로 차별 금지                                 |

**생년월일시(사주)는 직무 수행과 무관한 정보**다. 이를 구직자에게 요구해 채용 판단에 쓰는 순간
위 두 조항의 사정권에 들어간다. 서비스 제공자가 직접 처벌 대상이 아니더라도, **「채용 판단에 쓰라」고
설계·광고한 도구**는 사업자의 위반을 방조·유도한 것으로 읽힌다. `/business` 「채용·승진 적합도」를
오늘 삭제한 이유가 이것이다.

**살리는 방법 — 세 갈래로 나눈다**

| 갈래                                                        | 판정        | 근거                                                  |
| ----------------------------------------------------------- | ----------- | ----------------------------------------------------- |
| ① 지원자를 놓고 뽑을지 말지 판단 (「내 직원 사주 고르자」)  | 🔴 **금지** | 채용절차법·고용정책기본법 정면                        |
| ② **이미 함께 일하는** 사람과의 소통·관계 이해              | ✅ 허용     | 채용 국면이 아니다. 상대 동의 하에 «관계 이해»가 목적 |
| ③ **본인 사주만** 보는 「아랫사람 인연 흐름」 (대상자 없음) | ✅ 허용     | 타인 정보를 아예 쓰지 않는다. 자기 성찰 도구          |

> CEO 예시 「직원복이 없는 건지… 보는 눈이 없는 건지」는 **③으로 그대로 살아난다** — 이건
> 사장 본인 사주의 문제이지 누구를 심사하는 게 아니다. 오히려 원래 톤에 가장 충실하다.

**②에 반드시 붙일 문구·기능 제약**

- 카피에 금지: 「채용」 「뽑」 「면접」 「지원자」 「적합도」 「합격」 「승진 대상」 「선발」 「자를」.
- 결과에 금지: 등급/합불/서열(A·B·C, 적합·부적합) — **점수도 서열로 읽히므로 밴드만**.
- 화면 상단 고지(§9-4 강화 고지): 「이 풀이는 **이미 함께 일하고 있는 사람과의 소통**을 돕기 위한
  것입니다. 채용·평가·인사 결정의 근거로 사용할 수 없습니다.」
- 🔴 **기존 라이브 문구 1건 정정 필요**: `focus-groups.ts` `WORK.label` = 「직장 (같이 일해도 되는
  사람인가)」 — 「~해도 되는 사람인가」는 **선별 판단**으로 읽힌다. →
  **「직장 (어떻게 맞춰 일할까)」** 로 교체 권고. 같은 파일 `WORK.questions[0]` 「시너지가 나나요,
  소모가 되나요?」도 상대 평가형이라 「어디서 부딪히고 어디서 잘 맞나요?」로 완화 권고.
  (`BUSINESS` 군은 **근로계약이 아닌 동업·거래**라 채용절차법 밖 — 현행 유지 가능)

## 10. 썸네일 규격

### 10-1. 형식

| 용도               | 크기     | 배치                       | 파일                                  |
| ------------------ | -------- | -------------------------- | ------------------------------------- |
| 허브 와이드 (16:9) | 1024×576 | 허브 ① 상위 3장            | `public/theme-fortune/{id}-wide.webp` |
| 목록 타일 (4:3)    | 512×384  | `/analysis/theme` 목록 2열 | `public/theme-fortune/{id}-tile.webp` |

🔴 **제목 글자를 이미지에 굽지 않는다.** 이유 셋 — ①한글 렌더 품질이 불안정하다 ②문구는
법적 사유로 **빨리 고쳐야 할 수 있다**(9차 정정처럼). 이미지에 박혀 있으면 재생성이 필요하다
③다국어(i18n) 때 전량 재생성이 된다. 제목은 카드 위 **HTML 텍스트 오버레이**로 얹는다.

### 10-2. 생성 프롬프트 규율

기존 파이프라인(`scripts/shrine-assets/generate-icons.mjs`)의 문법을 승계하되 **드라마 썸네일**용
구도를 새로 정의한다. 이 프로젝트의 이미지 규율(관찰 가능한 사실만 · 메타 지시문 금지 · 방향 명시)을
그대로 따른다.

```js
const STYLE =
  'warm painterly watercolor illustration, soft K-anime aesthetic, gentle golden rim light and subtle warm glow, rich detail'
const BG_SCENE = 'deep warm dark background, no text, no letters, no watermark'

// 드라마 스틸 컷 — 인물이 있고 감정이 읽히는 한 장면
const posterPrompt = (desc) =>
  `Cinematic still from a Korean drama, 16:9 wide framing: ${desc}. ${STYLE}, ` +
  `single figure placed left of center facing right, camera at eye level, ` +
  `shallow depth of field with the background softly blurred, ${BG_SCENE}`
```

**작성 규칙 (위반하면 캐릭터 시트가 나오거나 방향이 뒤집힌다)**

1. **메타 지시문 금지** — `CRITICAL`, `must NOT`, `IMPORTANT`, `do not` 를 쓰지 않는다.
   («하지 마라»를 넣으면 모델이 지시서 자체를 그린다 — 실측된 실패 패턴)
2. **관찰 가능한 사실만.** 「지쳐 보이는」(해석) ✗ → 「책상에 팔을 괴고 모니터를 응시하는」(관찰) ○
   설명이 안 먹힐 때 문장을 늘리지 말고 **관찰 사실 1개를 추가**한다.
3. **방향을 반드시 명시** — `facing right`, `left of center`. 생략하면 회차마다 뒤집힌다.
4. **얼굴은 몸을 따라 돈다고 못박는다** — 인물이 옆을 볼 때 `head turned to follow the body`.
5. 문구·간판·숫자는 넣지 않는다(`no text, no letters`).
6. 실존 인물·브랜드·로고를 지시하지 않는다.

### 10-3. 검수

🔴 **육안이 정본이다.** 자동 검출을 신뢰하지 않는다(과거 교훈: 합격선==검출임계면 게이트가
구조적으로 통과한다). 판정은 **실제 렌더 크기**(허브 448px 폭)에서 한다 — 원본 1024에서 보면
전부 좋아 보인다.

🔴 **자산 교체 시 파일명 버전업 필수**(`{id}-wide-v2.webp`). 같은 이름 덮어쓰기는 폰 캐시가
옛 그림을 계속 쓴다(2026-08-10 실증).
