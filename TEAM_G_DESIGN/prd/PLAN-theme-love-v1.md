## 1. 배경 — 지금 「테마운세」는 테마가 아니라 카테고리다

코드 실측(`app/actions/ai/trend.ts` · `app/protected/analysis/theme/[type]/page.tsx`):

진단: **현행은 「무엇에 대한 운세인가」를 팔고 있고, CEO는 「내가 지금 못 자고 검색하는 그 한 문장」을
팔라고 한다.** 같은 엔진, 같은 데이터, 다른 절단면이다. 그래서 이 기획의 핵심은 새 AI가 아니라
**기존 엔진 출력을 질문 단위로 다시 자르는 렌즈(lens)** 다.

이 프로젝트에는 이미 실패 교훈이 있다 — 종합사주풀이 v1이 개별 엔진을 재사용하지 않고 자체
프롬프트를 새로 썼다가 "5만냥짜리가 2만냥짜리보다 얕다"는 진단을 받았다
(`PLAN-samhap-synthesis-v2.md` §1). **인기테마운세는 그 실수를 반복하지 않는다.**

## 3. 설계 — 「렌즈(lens)」 구조

### 3-1. 한 문장 요약

> 인기테마운세는 **새 엔진이 아니라 기존 엔진 출력의 절단면**이다.
> 테마마다 ①어떤 엔진을 돌리고 ②그 출력 중 어떤 축만 확대해 보여주고 ③어떤 4~5문에 답하는가만 다르다.

### 3-2. 자료 구조 — `LoveThemeSpec` (FocusGroup의 사촌)

`focus-groups.ts`가 이미 검증한 패턴(순수 상수 + 단위테스트 + 프롬프트 조립 분리)을 그대로 복제한다.

```
lib/domain/love-theme/
  themes.ts        // LoveThemeSpec 8종 — 순수 상수. 문구(데이터)만.
  lens.ts          // 결정론 투영 함수 — 새 명리 계산 금지, 기존 엔진 출력의 재배열만.
  __tests__/       // 테마 8종 전수 검증 + 금지어 회귀
```

```ts
export interface LoveThemeSpec {
  code: LoveThemeCode // 'ATTRACTS_ME' | 'SAME_TYPE' | ...
  title: string // 후킹 제목 (화면에 그대로)
  subtitle: string // 서브카피 1줄
  engine: 'SOLO' | 'PAIR' // SOLO=buildSajuContext 1회 / PAIR=+calculateCompatibility
  /** PAIR일 때 compatibility-engine에 넘길 기존 19종 관계값. 새 관계값을 만들지 않는다. */
  relationForEngine: string | null
  /** 문체·금지소재를 물려받을 기존 FocusGroup. 테마는 군을 새로 만들지 않는다. */
  focusGroupBase: FocusGroup
  /** 이 테마가 확대할 결정론 축 (lens.ts 함수 키) */
  lenses: LensKey[]
  /** 이 테마가 답할 질문 4~5개 — focusAnswers[] 와 1:1 */
  questions: string[]
  /** 테마 고유 금지 소재 (FocusGroup.forbidden 에 가산) */
  forbidden: string
  /** 「단정 아님」 안전 프레이밍 지시 — 프롬프트 필수 삽입 */
  safetyFrame: string
  cost: FeatureCostKey // 'saju'(2만냥) | 'wealth'급(5만냥) 재사용
}
```

**설계 규율 4가지**

1. **새 FocusGroup을 만들지 않는다.** `focus-groups.test.ts`가 「19종 관계값이 모두 한 군에 매핑」과
   「각 군은 질문 정확히 5개」를 강제한다. 테마는 `focusGroupBase`로 문체·금지소재를 상속만 하고,
   자기 질문은 `LoveThemeSpec.questions`에 따로 든다.
2. **새 관계값(19종)을 만들지 않는다.** PAIR 테마는 기존 `crush`/`dating`/`lover`/`marriage`/`spouse`
   중 하나를 `relationForEngine`으로 골라 `CATEGORY_WEIGHTS`를 그대로 쓴다.
   (가중치를 새로 만들면 8카테고리 합=1.00 계약이 깨진다.)
3. **`lens.ts`는 새 명리 계산을 하지 않는다.** 입력은 `SajuContext` / `CompatibilityEngineResult`
   두 개뿐이고, 출력은 그것들의 **재배열·라벨링**이다. 새 합충 규칙을 여기서 만들면
   `compatibility-engine.ts`와 두 개의 진실이 생긴다.
4. **캐시 키에 테마 코드를 넣는다.** 궁합 v3가 「같은 두 사람을 다른 관계로 다시 보면 캐시를 잘못
   재사용」하던 버그를 `focusGroup` 일치 조건으로 고쳤다(`app/actions/ai/compatibility.ts`).
   테마도 같은 함정 — 캐시 판정에 `themeCode`가 빠지면 「썸」 결과가 「결혼」 화면에 뜬다.

## 4. 공통 안전장치 — 법·윤리 (테마별 항목보다 먼저 읽을 것)

### 4-1. 상대방 동의 — 지금 코드에 아무 장치가 없다 🔴

실측: `app/protected/family/**` · `components/family/**` 어디에도 「상대 동의」 문구가 없다.
`app/privacy/page.tsx`도 **이용자가 제3자(가족·연인)의 생년월일을 입력하는 상황을 다루지 않는다**
(제4조는 회사의 제3자 «제공»만 다룬다). 연애 테마는 이 공백 위에 «상대의 마음»을 얹는 기능이라
가장 먼저 메워야 한다.

**필수 3종 (전 PAIR 테마 공통)**

1. **인연 등록 시 1회 고지 + 체크**
   「상대의 생년월일을 입력하실 때는, 알려주신 분의 양해를 구해주세요.
   해화당은 이 정보를 풀이에만 쓰고 상대에게 알리지 않습니다.」 (체크 없이 저장 불가)
2. **결과 화면 최상단 고정 1줄 — «관계의 결» 선언**
   「이 풀이는 두 분의 생년월일이 만드는 **기운의 결**을 읽은 것입니다.
   상대의 마음을 읽은 것이 아닙니다.」
   → 이 문장이 「이 사람은 당신을 좋아합니다」류 오독을 구조적으로 막는 앵커다.
3. **결과 화면 최하단 — «대화 실마리» 블록 (모든 PAIR 테마 필수 섹션)**
   판정을 결론이 아니라 **질문 3문장**으로 되돌려준다.
   예) 「이번 주에 이렇게 물어보세요 — ①요즘 나랑 있을 때 편해? ②연락 텀은 지금이 괜찮아?
   ③다음에 가고 싶은 데 있어?」
   → 「점괘를 근거로 상대를 판단」에서 「대화를 시작」으로 행동을 돌린다. **이것이 이 기획의 윤리 축.**

### L1. 「내가 좋아하는 사람 말고, 날 좋아해주는 사람」 — `ATTRACTS_ME`

CEO 지정 테마. 원문 「…만날 거야! 나를 좋아해주는 사주궁합 보기」에서 **「궁합」만 덜어냈다** —
이 테마는 상대 생년월일을 받지 않으므로(본인 사주만) 「궁합」이라 부르면 표시와 실제가 어긋난다.
「날 좋아해주는 사람」은 **화자의 바람**이지 특정인에 대한 단정이 아니므로 그대로 살린다.

1. **후킹 제목**: 「내가 좋아하는 사람 말고, **날 좋아해주는 사람**」
   (숏폼·공유용 롱버전: 「내가 좋아하는 사람 말고 날 좋아해주는 사람 만날 거야 — 나를 편안해하는 사람의 결」)
2. **서브카피**: 짝사랑만 하다 지쳤다면. 내 사주가 편안해하는 사람의 결을 봅니다.
3. **썸네일**: 등불 아래 낮은 찻상, 찻잔 둘, **맞은편 방석은 비어 있고 빛이 그 위로 번진다.**
   ```
   {BASE}, a low walnut tea table lit by an oil lamp, two celadon tea cups placed on it,
   one floor cushion on the near side holding a folded ivory shawl, the cushion on the far
   side empty, warm lamplight spreading across the empty cushion, seen slightly from above,
   the lower third of the image is smooth plain hanji paper, square composition
   ```

   → **동의 이슈 없음 · 진입 장벽 최저 → 연애 라인업의 관문(무료 회원 유입구)**.

## 6. 복채 단가 — 기존 체계와의 정합

`feature-costs.ts`는 2만냥 / 5만냥 두 칸뿐이다(관상·손금·풍수·사주·궁합=2 / 재물·이미지·삼합=5).
**테마는 새 칸을 만들지 않는다.** 배정 규칙 한 줄:

> **AI 호출 1회 + 엔진 1~2개 = 2만냥. 여러 해의 세운 타임라인까지 도는 「결정용」 리포트 = 5만냥.**

| 테마       | 엔진 호출                                                                         | 단가 | 근거                                               |
| ---------- | --------------------------------------------------------------------------------- | ---- | -------------------------------------------------- |
| L1, L2     | `buildSajuContext` ×1                                                             | 2    | 사주(2만냥)와 같은 무게                            |
| L3         | `buildSajuContext` ×1 + `calculateYearlyFortune` ×1개년                           | 2    | 신년운세가 무료라 시기 테마를 5로 올리면 체감 모순 |
| L4, L5, L7 | `buildSajuContext` ×2 + `calculateCompatibility` ×1 (+ 월운·1개년 세운은 최대 ×2) | 2    | **현행 궁합과 동일 비용 구조 → 동일 단가**         |
| L6, L8     | 위 + `calculateYearlyFortune` ×2인×3개년 + `findKeyMonths`                        | 5    | 삼합(5만냥)과 같은 「여러 엔진 교차」 등급         |

🔴 **이 표의 L 번호는 7종 시절 번호였다(정정 완료).** 옛 표기는 「2만=L4·L6 / 5만=L5·L7」이었고 그때의
L5·L6·L7은 각각 결혼·위기·재회를 가리켰다. L5(`TEXT_OR_NOT`)가 삽입되면서 번호가 한 칸씩 밀렸을 뿐,
**엔진 호출 묶음과 단가 배정은 그대로다** — 썸 2 / 연락 2 / 결혼 5 / 위기 2 / 재회 5.
괄호 안의 「월운·1개년 세운 최대 ×2」는 L4(월운 2회)·L5(월운 2회)·L7(올해 세운 2인)이 실제로 쓰는
호출을 명시한 것이다. **결정론 계산은 CPU만 쓰고 AI 호출을 늘리지 않으므로 등급을 올리지 않는다** —
등급을 가르는 것은 「여러 해 타임라인을 도는 결정용 리포트인가」이지 함수 호출 수가 아니다.

`FeatureCostKey` 신설 없이 표시 함수만 재사용한다(`formatFeatureCost`). 새 키를 만들 거면
**`feature-costs.ts`·`MISSION_CATEGORY_TO_COST_KEY`·실차감 3곳을 동시에** 고쳐야 표시=실차감이 유지된다.

🔴 **환불 규칙 승계**: 캐시 히트 시 환불(수익화 v2 규칙)을 테마도 따른다. 캐시 키에 `themeCode` 포함(§3-2).
