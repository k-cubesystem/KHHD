## Problem Statement

한국 전통 프리미엄 리디자인이 3개 화면(만세력·메인 대시보드·사주 카드)까지 출하됐다.
다음 단계로 "잔여 ~20화면 전수 확산"이 후보였으나, 세션 중 두 가지가 확인됐다:

1. **관찰 증거 0건** — 새 전통풍 화면을 실유저가 쓰는 것을 본 적 없음 (배포 직후).
2. **해자 테제의 자기모순** — 창업자 테제는 "AI 풀이는 커모디티가 되고 의례감·세계관이
   해자, 전통풍 디자인은 그 외피"인데, 원안은 외피(디자인)를 20화면에 도포하는 것.
   해자가 의례라면 최고 레버리지는 의례 루프 자체를 짓는 것이다.

따라서 이번 단계의 문제는 "화면을 더 칠하는 것"이 아니라 **"의례가 실제로 사람을
다시 오게 하는가의 증거를 만드는 것"**으로 재정의됐다.

  없는 가설**이다 (표본 7명 — 반증도 아님, 미검증).
- 경쟁 랜드스케이프: 점신·포스텔러는 무료 콘텐츠 물량(6,000건+)+AI 해석+굿즈로 경쟁.
  "의례감·공간"으로 리텐션을 사는 플레이어는 없음 → 차별화 여지 실재.

## Status Quo

- 유저는 분석(사주 풀이) 후 이탈한다. 매일/매달 돌아올 구조화된 이유가 없다.
- 신당·복 생태계(bok_points, bok_missions, 웹푸시)는 존재하지만 "정기 의례"로
  묶이는 단일 루프가 없다.
- 전통풍 디자인은 3개 화면에만 적용 — 동선 중간에 구스타일 화면이 끼어 세계관이 끊긴다.

## Target User & Narrowest Wedge

- **1차 가설 타깃(강등됨)**: 가족 사주를 챙기는 40-50대 여성 — 검증 대기 가설.
- **실측 현재 유저**: 본인 사주를 반복 조회하는 자기점(自己占) 유저 (82%).
- **쐐기**: 「초하루 의례」 단일 루프 — 매달 초하루에 (1)식구/본인 운세 1줄 카드 →
  (2)신당 기원 1탭 → (3)복 장부 축적. **본인 카드가 항상 첫째**라 자기점 유저도
  완전한 의례가 가능하고, 「+식구 모시기」 진입점이 가족 가설의 검증 지점이 된다.

## Premises (합의됨)

1. ~~타깃·행위 전환 승계~~ → **수정: "가족 복 관리 행위"는 검증 대기 가설.** 설계는

   결과가 나쁘면 확산 중단.
4. 단일 출처 — 모든 화면은 DESIGN.md 토큰·컴포넌트만 사용.
5. 기술 제약 — styled-jsx 금지 / prod 빌드 CSS 검증 / use server 상수 export 금지.

## Approaches Considered

### Approach A: 의례 동선 4화면만 (최소)

전통풍을 동선 4화면으로 한정 + 계측. 루프 신설 없음. — 기각: 해자(의례)를 깊게
만들지 않음. Completeness 5/10.

### Approach B: 초하루 의례 루프 + 동선 확산 (이상)

의례 루프 신설 + 계측 + 전통풍은 의례 동선 4화면만. Completeness 9/10.

### Approach C: 전수 확산 (원안)

잔여 ~20화면 전부 + 에셋 파이프라인. — 단독 채택 기각: 관찰 증거 0인 방법의 복제,
매출 직결성 간접적. Completeness 7/10.

## Recommended Approach: B+C 하이브리드 (사용자 선택)

**1단계 (지금): Approach B**

- **착수 브랜치 확정(T1)**: `claude/determined-yonath` — git 실측으로 main은 이
  브랜치의 엄격한 조상(main 고유 커밋 0, yonath 고유 449)이고 프로덕션 배포
  브랜치다. 신당 무대·웹푸시 자산이 모두 존재하므로 구(舊) (b) 경량 씬 폴백
  경로는 **삭제**. main 착수는 프로덕션에 도달하지 못하므로 금지.
- `/protected/ritual` 초하루 의례 루프: ①진입(식구/본인 카드 가로스크롤, 본인 첫째)
  → ②기원(신당 무대 컴포넌트 임베드. 신당 페이지로 이동하지 않음 — 루프 이탈 방지.
  향 올리기 1탭 → 기원 누적 +1 · 복채 적립) → ③복 장부(월별 축적, 연속 기록, 빈달 표시,
  다음 초하루 웹푸시 구독 CTA).
- **진입 동선(T4)**: ritual_enter 이전 3접점 — (1) 대시보드 D-day 배너(의례 창
  내 강조 상태), (2) 일간운세 화면에 초하루 안내 1줄, (3) 초하루 웹푸시.
  인지 없는 빈달은 리텐션 장치가 아니므로 진입 동선은 1단계 범위다.
- **완주 판정(단일 정의)**: 기원 서버 액션 성공 = `ritual_complete` 이벤트 발화 =
  `ritual_records.completed_at` 기록. 세 가지는 항상 같은 시점.
- **초하루 정의(확정)**: 음력 초하루(朔日). 만세력 엔진의 음력 변환(lunar-javascript
  `solar.getLunar().getDay()===1`)을 재사용. **판정과 발송 분리**: 일일 크론이
  음력 1일 여부를 판정하고, 발송 시각은 07:00 KST(기존 daily-fortune 크론과 동일
  슬롯) — 자정 발송 금지. (양력 1일 폴백은 엔진 재사용이 불가능하다고 판명될 때만.)
- **의례 창**: 초하루 포함 3일. 창 밖 진입 시 복 장부 + 다음 초하루 D-day 표시
  (읽기 전용). 놓친 달 소급 없음 — 빈달이 보이는 것 자체가 리텐션 장치.
- **멱등성**: 기원 적립은 유저·음력월(윤달 구분 포함)당 1회, 서버 측 강제
  (`ritual_records` unique(user_id, ritual_month, is_leap_month) + 서버 액션 검증).
- GA4 퍼널: `ritual_enter → member_card_view → pray_tap → ritual_complete` +
  푸시발 재방문 태깅 + `family_invite_from_ritual`(가족 가설 검증 이벤트) +
  `ritual_push_optin`(구독 CTA 탭).
- 같은 배포에서 기출하 3화면에도 계측: 각 화면 `screen_view` + 핵심 액션 1개 —
  만세력 `manse_tab_change`, 대시보드 `dashboard_cta_tap`, 사주 카드 `saju_card_open`.
- 전통풍 확산은 의례 동선 **3+1화면**(대시보드→운세→신당 + `/protected/ritual`
  자체 — 의례 루트는 전통풍 100%)까지. **상점은 1단계에서 제외** — 결제 화면
  회귀 리스크 때문. 상점 전통풍 전환은 2단계 후보이며 결제 e2e 통과가 머지 조건.
- 와이어프레임 승인됨 — `docs/designs/ritual-loop-wireframe.html` (3화면 구성,
  레포에 보존).

**2단계 (게이트 뒤): 재결정 (T2로 완화)**

- 판정선(아래 Success Criteria) 충족 시 **자동으로 C(전수 확산)를 착수하지 않고**,

## Success Criteria (2단계 게이트)

루프 출하 후 2회의 초하루(약 2개월) 관찰:

- **전제 조건**: 푸시 구독자 ≥ 5명. 미달 시 게이트 판정 보류하고 전체 유저 기준
  보조 지표(의례 창 내 ritual_enter 유저의 완주율)만 관찰. 구독 유도는 의례 완료
  화면(③)의 「다음 초하루에 알려주오」 CTA가 담당 — `ritual_push_optin`으로 측정.
- 의례 완주율(의례 창 내 ritual_enter → ritual_complete) ≥ 40%
- 완주자의 다음 초하루 재방문율 ≥ 50% — **측정 범위 주의**: 2회 관찰로는 1차
  초하루 완주 코호트만 측정 가능(2차 완주자의 "다음"은 관찰창 밖). 코호트 1개·
  표본 수 명 기준임을 전제로 판단.
- 보조: 「+식구 모시기」 탭률 — 가족 가설의 방향 신호 (판정선 아님, 관찰 지표)
- 보조(T6): 의례 완주자의 유료 풀이 전환 — 관찰 지표 (돈이 되는 루프인지의 방향 신호)
- 정성: 실유저 최소 1명 직접 관찰 1회 완료 (전제 3 이행)
- **판정 데이터 소스(7A)**: 완주율·재방문율은 GA4가 아니라 `ritual_records`의
  entered_at/completed_at **DB 기준 SQL로 판정**. GA4는 UX 퍼널 보조.
  표본이 작으므로 수치는 기계적 컷이 아니라 판단 보조선 — 단, "측정 없이 확산 없음"은 기계적.

  wish_category(기존 `shrine_wishes` 6종 재사용)
  - unique(user_id, ritual_month, is_leap_month) + RLS(본인 SELECT만, INSERT/
    UPDATE 정책 없음 — 쓰기는 `complete_ritual`/`enter_ritual` SECURITY DEFINER

    어디에도 저장하지 않는다 · 스키마에 텍스트 컬럼을 만들지 않는 것으로 강제한다"를
    명문화했고 수집 사유(실물 굿 O2O)는 보류로 소멸. 유저가 쓴 문장은 클라이언트에서
    소원 카드 연출로만 쓰이고 서버로 전송되지 않는다. 서버가 아는 것은 wish_category뿐.
- **`complete_ritual` RPC의 계약 (Eng 10A·11A — 단일 트랜잭션 3단계)**:
  1. `ritual_records` upsert — unique(user_id, ritual_month, is_leap_month)가
     **음력월 멱등의 유일한 게이트**. 이미 완주한 달이면 여기서 no-op.
  2. `record_shrine_devotion(p_user_id, <KST 오늘>)` **호출** — 누적 적립.
     **KST 일 멱등은 이 함수 안에만 존재하며 재구현하지 않는다**(반환값
     `(gained boolean, total_days int)`을 그대로 읽는다). 신당 페이지에서 오늘 이미
     기원했다면 `gained=false`로 no-op 되지만 **의례는 정상 완주**한다 — 두 멱등은
     서로 다른 질문("이 달의 의례를 했나" / "오늘 적립했나")에 답하므로 이중화가 아니다.
  3. **복채 적립** — 기존 `add_bokchae` 경로(wallets + wallet_transactions).
     적립량은 `system_settings` 조회(클라 입력 불신), 액션은 인자를 받지 않으며
     지급은 server-only 모듈 경유. **`bok_points`가 아니라 복채(wallets)** —
     `lib/services/bokchae.ts`의 "단일 통화(복채) 정책"과 라이브 실측(wallets 7명
     전원 보유 / bok_points는 소비처 없는 tier 게이지)에 따름. 새 원장을 만들지
     않으므로 이원화 금지 원칙은 유지된다.
  - 실패 순서: 1이 실패하면 2·3을 시도하지 않는다. 부분 성공이 남으면
    「향은 올라갔는데 장부는 빈달」이 무증상으로 발생한다(Eng 실패모드 #1,
    critical gap). `ritual-grant.ts`의 `complete_shrine_vow` 패턴을 따른다.
- 만세력 엔진의 음력 변환 — 초하루 판정에 재사용.
- 신당 무대 컴포넌트 · `record_shrine_devotion` · `add_bokchae` — 재사용(신규 지급 경로 없음).
- GA4 이벤트 체계 — 기존 체계에 이벤트 추가.
- assets-src/sharp 파이프라인 — 비의존(별도 트랙, 2단계에서 합류).
